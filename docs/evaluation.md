# M6 对照实验与交付

本仓库的评估组件只计算已有样本，不能替代真实 agent、Linux VM 或 eBPF 控制实验。
仓库当前不含 20 个真实任务、两个 agent 各 10 个任务、每任务三次的结果；因此不得把
离线夹具、模板、单元测试输出或 `validate_manifest` 的空问题清单写成 M6 验收已通过。

[`benchmark-manifest.example.json`](benchmark-manifest.example.json) 是**未执行**的填写模板：
它规定样本槽位、字段和产物位置，不包含测量结果，更不是可由仓库直接执行的 runner。
真实运行应从该文件复制出一份不纳入版本控制的 manifest，并保留其输入、原始事件与失败证据。

## 指标口径

`ConfusionMatrix` 始终保留 TP、FP、FN、TN。precision 使用 `TP/(TP+FP)`，recall
使用 `TP/(TP+FN)`，FPR 使用 `FP/(FP+TN)`；分母为零时结果为 `None`，而非零或通过。
区间为确定性的双侧 95% Wilson score interval，报告中同时保留分子和分母。

`classify` 接收 `(truth, prediction)`；任一为 `None` 的样本会作为排除数返回，绝不
伪装为 TN。真值须来自受控操作预期、结果验证、测试服务记录或人工复核，并另行记录
来源。应用日志、纯外部观测、外部观测加标记需要分别以统一语义事件计算矩阵。

性能样本是 `(elapsed_ms, cpu_time_ms, peak_memory_bytes)`。p50/p95 使用排序样本的
线性插值，峰值内存报告最大值。每项允许独立缺失，但缺失不代表零；本地固定负载和远端
LLM 负载必须分开汇总，避免网络等待稀释探针开销。

## 实验清单与最小样本

`ExperimentRun` 固定记录输入摘要、环境、策略、模型配置、是否真实 agent、结果是否已
记录和缺失输入。`validate_manifest` 默认检查计划门槛：20 个真实任务、至少两个 agent、
每 agent 10 个任务、每 agent/任务 3 次重复。它返回问题清单，绝不自动补全样本或将夹具
算作真实运行。

真实交付还须保存脱敏原始数据、失败样本、异常集（子进程、容器、并发、临时替换、重试、
断流、过载、越界）、消融配置和许可证清单。真实模型运行应另外记录凭据可用性与实际费用
前提；费用估算不能称为账单。

每一条已运行记录至少填写：`task_id`、`agent_id`、`repetition`、`kind`、`input_digest`、
`environment_id`、`policy_id`、`model_config_id`、`is_real_agent`、`outcome_recorded`，以及
原始产物的相对路径。`input_digest` 是固定任务输入的哈希，不得用提示词标题替代；模型配置
应固定提供方、模型版本、温度、最大 token、工具版本和重试预算。每次失败、超时、人工中止
和不可用凭据都是结果，必须记录原因与原始证据路径，不能从分母删除。

模板将 20 个任务槽位分给两个具名 agent，各 10 个；每槽位连续运行 3 次。若同一任务需要
被两个 agent 都执行，可新增任务/agent 组合，但不可借此减少 20 个不同 `task_id` 的门槛。
任务输入应包含预期操作、成功判定、允许副作用和真值来源；涉及真实服务时还应记录服务端
请求日志和实际费用导出时间。

## 对照、真值与异常集

每个真实任务和每个异常样本都要以相同任务边界、文件边界和请求边界分别生成三组结果：

| 对照组 | 输入 | 必须报告 |
|---|---|---|
| `application_logs` | agent/应用自行产生的结构化日志 | 漏记、误记、无法映射的语义事件 |
| `external_only` | 不使用辅助标记的外部事件观测 | 同一真值下的 TP/FP/FN/TN、歧义和覆盖率 |
| `external_with_markers` | 外部观测加辅助标记 | 与前两组相同口径，另列标记缺失/冲突 |

不得将 syscall 数与一个高层“文件已修改”日志条目直接相除。先将各来源映射为同一类语义事件
（任务、请求、文件读写、网络目的地、策略决定和中断），再逐项与独立真值比对。真值来源要
写明是受控操作预期、结果/文件快照、测试服务记录或人工复核；辅助标记不得是唯一真值。

异常集必须独立于真实任务汇总，至少覆盖：子进程、容器、2/5 路并发交错、临时文件替换、
重试、断流、过载和越界操作。每个用例保存注入步骤、预期事件/拒绝、实际系统调用返回或
文件快照、服务端记录（如适用）及清理状态。M5 的阻断结论仅在真实内核控制加载后，且由
返回值和内容验证时才可声明；当前 Python 策略对象不构成该证据。

## 消融与性能

消融按顺序运行 `time_window`、`process_lineage`、`container_mapping`、`auxiliary_markers`，
每一步只增加该项能力，固定任务、环境、策略和模型配置。对每一步分别保存指标变化、歧义、
失败条件和额外资源成本；未采集到的字段标为缺失，不填零。

性能组使用五个配置：`no_probe`、`system_probe`、`system_probe_tls`、`full_audit`、
`control_enabled`。本地固定负载与远端 LLM 负载分开运行、分开汇总；每次运行记录 wall-clock
耗时、CPU 时间、峰值内存、负载参数、采样窗口与丢失计数。报告 p50、p95、最大内存以及
95% Wilson 区间的分子/分母；网络等待不能用来抵消探针开销。

## 复现与交付核对

一次可审计交付至少包含以下目录（敏感内容可脱敏，但摘要和相对路径必须保留）：

```
evidence/m6/
  manifest.json                 # 从 example 复制并填写，status 不再是 planned
  environment/                  # VM、内核、镜像、包、git revision、时钟信息
  inputs/                       # 固定输入及 sha256 摘要
  truth/                        # 预期、快照、服务端记录、人工复核说明
  raw/                          # 脱敏账本、probe/应用日志、系统调用或审计交叉证据
  results/                      # 三组对照、异常、消融、性能的逐运行结果
  failures/                     # 失败、超时、中止及复现命令
  licenses/                     # agent、模型 SDK、镜像和数据的许可证/版本
```

在干净 Linux ARM64 VM 中，先按 `docs/00-env.md` 建立环境并记录 `probe doctor --json`；随后
固定 manifest 中的输入和配置，运行两个 agent，收集所有三次重复的原始证据，再把记录构造成
`ExperimentRun` 交给 `validate_manifest`。该函数只报告缺口，**不**验证采集真实性、不会读取
JSON，也不会替代真值审计。发布前执行完整测试集，并在演示中展示“尝试越界 → 拒绝原因 →
agent 合规重试 → report/explain 证据”；若任一前提未满足，交付实际数据和限制，而非通过声明。
